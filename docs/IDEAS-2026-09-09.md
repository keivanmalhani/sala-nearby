# Sala Nearby: ideas past the list

Written 2026-09-09 against the live app and the live APIs, not against memory. Every
"the data exists" claim below was fetched; every "it does not" was probed and got a
refusal I can quote.

He asked for showtimes, pricing, interactive maps, snack lists, drink lists, screen
information, projection type in normal words, audio information, seats and auditorium
info, movie info, loyalty programs and points, dress code, average theater temperature,
online reviews and alcoholic drinks -- and then for more ideas than that. This document is
the more, plus an honest verdict on three of his own items that the data cannot support.

---

## 1. What grounding this turned up first

Three facts changed what is worth building, so they come before the ideas.

**The payload is much bigger than the page's own comments say.** The published build is
stamped `2026-09-09T07:14` and carries **11,252 showings, 89 films, 35 cinemas, 30 days**.
The source comment still says 5,445. Both the file on disk and the live URL agree, checked
independently.

**70% of everything playing is dubbed.** Across the whole payload: **3,317 subtitled
showings against 7,750 dubbed**, 185 neither. That is the single most decision-shaping
number in the data and the app currently treats it as one chip among six.

**A returning visitor gets one launch of yesterday's listings.** My first pass on the live
URL was served the `2026-09-08T14:45` build out of the service worker cache while the
network had the 07:14 one. This is the trap `test-sw-freshness.js` already documents --
GitHub Pages sends `cache-control: max-age=600` on index.html, so `cache.addAll` can
faithfully cache the old page -- so it is a known thing and not a discovery. Worth
re-running that control after the next refresh.

## 2. Where the app is thin, from using it

The app is good. Filters, search, the day rail, the film sheet listing every cinema that
plays a film nearest-first with its room numbers -- all of it works, on a 393-point
screen, and the restraint in the design is the best thing about it. Five thin spots, all
found by driving it:

- **The same film can appear twice.** La Odisea is in the payload under two ids, one per
  chain, and the Cineteca showings are severed from the Cinemex ones. Seven titles are
  affected. This is idea #4 and it is the one outright bug in the list.
- **The filters are strictly single-select.** `S.filter` is one string and `passes()`
  switches on it. Clicking Subtitled then IMAX leaves only IMAX pressed. There are **126
  subtitled IMAX showings** in the payload and no way to ask for them.
- **Search reads titles only.** "odyssey" finds La Odisea (it matches the original title,
  which is a nice touch), but "nolan" returns 0, "delta" returns 0 and "imax" returns 0.
  The director is in the data as `dir` and is not searched -- and see #19, because
  searching it would not have helped either.
- **The map's colours no longer decode.** Markers are four colours -- green for
  independent, orange for large-format, purple for Platino/VIP, blue for standard -- and
  the legend was removed on his say-so, so the encoding is now unreadable. The answer is
  not to put the legend back.
- **Nothing in the app knows about a festival.** "Ambulante", "FICUNAM" and "MICGenero"
  appear only as prose inside venue write-ups. MICGenero's CDMX tour is running **right
  now, through 11 September**, and the app cannot see it.

## 3. What the data will and will not support

This section decides most of the ranking, so it is receipts rather than summary.

Control first: `/cinemas/` returns 200 and 227,943 bytes, so the 400s below are wrong
paths and not a dead key.

**Fields Cinemex publishes that the app does not use:**

| Field | Coverage | Worth anything? |
|---|---|---|
| `info.trailer` | 50 of 51 films, YouTube URLs | yes |
| `info.cast` | present on all | yes |
| `info.country`, `info.distributor` | present on all | yes |
| `popularity` | 51 of 51, real integers | maybe |
| cinema `attributes` | all 70 CDMX sites: `3d` 45, `premium` 17, `platinum` 14, `cx` 11, `market` 6, `art` 4, `4d` 3 | yes, this is the big one |
| `alt_cinemas` | 17 of 70 CDMX sites | yes |
| `info.map_link` | all, carries a Google place id | yes |
| `auditorium_number` | every session | yes, already shown |

**Fields that exist and are dead -- do not build on these:** `score` is 0 on all 51 films.
`colors` is present on all 51 and every value inside is `null`. `info.hours` is empty on
all 70 CDMX cinemas. `poster_mp4` and `poster_gif` are null. `info.imdb_url` is an empty
string.

**Endpoints that do not exist.** Every one of these returned
`400 {"errorcode":"unexpected-error","error":"No route found ..."}`: `/candybar/`,
`/candybar/products`, `/cinemas/30/candybar`, `/products/`, `/menu/`,
`/cinemas/30/products`, `/sessions/<id>/seats`, `/seats/<id>`, `/prices/`,
`/cinemas/30/prices`, `/loyalty/`, `/promotions/`, `/coming-soon/`.

**`candybar` is `false` on all 70 CDMX cinemas**, and `cinemex.com/dulceria` is a 404
("Lo que sea que estes buscando no esta por aqui"). There is no machine-readable snack
menu. That is not a gap in my searching; it is the answer.

**A small correction to CINEMEX-API.md.** The version in the path is not validated at all.
`v2.37.2`, `v2.38`, `v9.99.99` and `vBANANA` all return byte-identical 126,004-byte
responses, same md5. Their own web client now calls `v2.38`, but being pinned to `v2.37.2`
is a non-finding, not drift. The doc's point still stands -- the segment has to be
*shaped* like a version -- it just is not a version.

**Outside sources that are genuinely free and forever-free:**

- **CDMX GTFS static**, `datos.cdmx.gob.mx/dataset/gtfs`: Metro, Metrobus, Trolebus, RTP,
  Tren Ligero, Suburbano, Cablebus, Pumabus. Static needs no key. Metrobus GTFS-RT needs
  a free registration.
- **TMDB** watch providers, per-region, Mexico supported, JustWatch-sourced. Free for
  non-commercial use with a key; attribution to JustWatch is required and it returns
  availability rather than deep links.
- **Google place ids and ratings** via the `tbm=map` endpoint the Maps frontend itself
  calls -- `tools/find-places.py` already does this, no Places API key, so no metered
  billing.

## 4. The ideas, ranked

Rank is my judgement of value to him divided by work, not a score out of ten. Build
difficulty is against the app as it stands: one self-contained HTML file, data baked at
build time by Python, no framework.

### 1. Leave-by time instead of walking distance

**What it is.** Every time chip also answers "when do I leave", computed from the walk
time the app already has plus the ad reel: `20:30` becomes `leave 20:11`.

**Why him.** He is about to live four minutes from Cinemex Insurgentes and twenty-three
from Parque Delta, on foot, in a city where the billed time is not the start time. The app
currently gives him two numbers -- "20:30" and "23 min walk" -- and makes him do the
arithmetic every single time. This is the difference between a listings page and something
that tells him what to do.

**Data.** All local. Walk time is already computed per cinema. The one unknown is the ad
allowance, which is a per-chain constant he can measure once (Cinemex runs roughly 15-20
minutes; Cineteca starts close to on time, which is itself worth saying out loud).

**Build.** Small. One function, one constant per chain, and a second line on the chip.
The only real design question is not showing it on chips that have already started.

### 2. Filters that stack, and subtitled as a saved default

**What it is.** Make the filter chips additive instead of mutually exclusive, and let
"subtitled" persist across launches the way the theme already does.

**Why him.** Subtitled versus dubbed is a real decision on every film in this city, and
the data says the default is against him: **7,750 dubbed to 3,317 subtitled**. He is not
choosing a filter, he is stating a standing preference. Today he cannot express "subtitled
IMAX" at all, and 126 such showings exist.

**Data.** Entirely in the page. `lang_sub` and `lang_es` are already types on every
format.

**Build.** Small, and the best value-to-work ratio in this document. `S.filter` becomes a
set, `passes()` becomes an `every`, `filterCounts()` needs to count against the set, and
the existing disabled-chip logic keeps working. `localStorage` already holds `sala.theme`,
so the persistence pattern is there.

### 3. Which room, not just which cinema

**What it is.** The time chip says `20:50 Sala 10`; make the app say that Sala 10 is the
CinemeXtremo room with Dolby Atmos, and mark the good rooms on the list.

**Why him.** This is his own "seats and auditorium info" item, in the one shape the data
actually supports, and it is the app's whole reason to exist. No ticketing app knows that
Parque Delta sala 3 is the IMAX with Laser and sala 10 is the CX Atmos room. His audit
already knows. The showtimes already carry the sala. The two have never been joined.

**Data.** Both halves are in the page. Sessions carry `auditorium_number` for all 11,252.
The audit names specific salas in **5 of 42 venues** -- Parque Delta, Antara, Reforma 222,
Universidad, Patriotismo -- which is exactly the set where it matters. The audit side is
prose today and needs a small structured table.

**Build.** Small to medium. The work is the per-sala table for those five or six venues,
not the code.

### 4. One film, one entry, across both chains

**What it is.** Merge films that the two chains publish separately, so a title appears once
and its Cinemex and Cineteca showings sit in the same list.

**Why him.** This is a bug before it is a feature, and it hits the exact case he cares
most about. **La Odisea is in the payload twice**: id `71948` from Cinemex, 264 showings
across 25 cinemas, director recorded as "Christopher Nola"; and id `ct-HO00009759` from
Cineteca, 12 showings across two sedes, director recorded correctly as "Christopher
Nolan". Both carry the original title `The Odyssey`. So the Films tab lists it twice, and
the film sheet that promises every cinema nearest-first silently omits Cineteca.

**There are 7 such collisions**, six across the two chains and one inside Cineteca alone:
la odisea, coyote vs acme (three ids), las catadoras de hitler, sobre las olas,
adolescencia sexo y muerte en campamento miasma, lo que queda de ti, and ponyo y el
secreto de la sirenita.

The reason this matters more than seven rows suggests: a Cineteca screening of a film is
almost certainly subtitled, and the Cinemex run of the same film is 70% dubbed. Merging
them is how the subtitled question gets its best answer -- and it is a prerequisite for
both #6 and #7, because the rare-screening and festival views are meaningless if the same
film counts as two.

**Data.** Already in the page on both sides. `o` (original title) is populated for both
entries and matches exactly, which makes it the join key. Fall back to folded title plus a
duration within a few minutes -- the two Odyssey rows read `2h55m` and `2h52m`, so an exact
duration match would fail.

**Build.** Small, in the Python that bakes the payload rather than in the page. Guard it
the way the refresh guards are already written: assert that merging never reduces the
distinct film count by more than a handful, or a loose fold will one day collapse two
genuinely different films into one.

### 5. Can I get home from this showing

**What it is.** Flag any showing whose end time lands after the last Metro or Metrobus
that serves the cinema.

**Why him.** A 21:40 IMAX at Parque Delta ends near midnight and Line 9 stops running. He
does not live there yet and will not have the reflex for a year. Every chain app sells him
the ticket and says nothing.

**Data.** CDMX GTFS static, verified above, covers Metro and Metrobus with stop times, no
key. Film duration is in the payload as `d`. Nearest station per cinema is a one-time
computation from the GTFS stops file.

**Build.** Medium. Parsing GTFS once at build time and baking a last-service time per
cinema is straightforward; the honest hard part is that GTFS schedules and reality differ,
so the copy has to hedge without being useless.

**Nothing in the world does this**, which is the argument for it.

### 6. The screenings that happen once

**What it is.** A view of everything playing exactly once or twice in the next month,
ordered by date rather than grouped by cinema.

**Why him.** The showtimes grid is built for a film with 30 showings a week. It is the
wrong shape for repertory, and repertory is what Cineteca and the cineclubs do -- a film
plays Thursday at 17:00 and never again, and you miss it by not looking on the right day.
The payload already contains **93 film-and-cinema pairs with exactly one session**, and
**25 of 88 films have three or fewer showings in the whole 30 days** -- Moana live action,
Queer Shorts 2, Nosotras las taquigrafas. Those are the things worth knowing about in
advance and they are currently buried under Resident Evil: Noche Cero's 1,790 showings and
Coyote vs Acme's 1,568.

**Data.** Already in the page. It is a `groupBy` and a sort.

**Build.** Small. This is Mubi's editorial instinct applied to data he already ships, and
it needs no new source at all.

### 7. Festivals, as dates rather than prose

**What it is.** A small hand-kept table of festival name, dates, venues and URL, surfaced
when one is running.

**Why him.** MICGenero's CDMX tour is on **through 11 September 2026** and the app cannot
see it. FICUNAM 16 runs **5-15 November**, which is after he moves. Ambulante 21 was 5-14
March. These play at venues already in his V array -- Cine Tonala, La Casa del Cine, Centro
de Cultura Digital, Casa del Lago -- as audit-only entries with no showtimes, so the app
knows the room and not that something is in it. This is the thing a chain app will never
have, and it is most of why someone would open this app instead of Cinemex's.

**Data.** No API. FICUNAM publishes a programme page; the rest publish PDFs and Instagram.
Realistically this is six to eight rows of hand-entered JSON per year.

**Build.** Small to build, ongoing to maintain. Be honest with him that the upkeep is the
cost, and that a stale festival card is worse than none.

### 8. The fields already being thrown away

**What it is.** Put the trailer, cast, country and distributor on the film sheet.

**Why him.** `info.trailer` is populated on **50 of 51 films** and the app ships none of
them. Country matters here in a way it does not in the US -- whether something is a Mexican
film is often the reason to go.

**Data.** Already fetched on every refresh and discarded.

**Build.** Small. One caution: link out to YouTube rather than embedding, because an embed
breaks the offline story and adds a third party to a page that currently has none.

### 9. Projection and sound in normal words

**What it is.** A plain-language line for each format: what IMAX with Laser, CinemeXtremo,
Infinity Vision, Platino, Market and Casa de Arte actually mean to a person.

**Why him.** He asked for it, and the app is already half way there -- `PLAIN[]` does
exactly this per venue and there is a glossary for Casa de Arte. What is missing is the
per-format version, which is the one he keeps hitting.

**Data.** All present. `attributes` gives the machine-readable tags; the words are the work.

**Build.** Small code, real writing. This is a copy job and should be treated as one.

### 10. Extend the audit to every Cinemex in the city, for free

**What it is.** Use the API's own `attributes` array to give all 70 CDMX Cinemex sites a
format profile, with the 42 hand-audited venues as the premium layer on top.

**Why him.** He hand-researched 42 venues. Cinemex publishes machine-readable format tags
for 70 and he is using none of them. It also cross-checks his own audit: if the API says a
site is `premium` and the audit says it is not, one of them is wrong and that is worth
knowing.

**Data.** One request, already being made.

**Build.** Medium, mostly in deciding how to show a venue that has tags but no write-up
without it looking like a hole.

### 11. Nearby by Metro, not by crow-flies

**What it is.** Sort cinemas by real travel time, not haversine distance.

**Why him.** Parque Delta reads "1.7 km, 23 min walk" and is two stops on Line 9. WTC
reads 2.5 km and is genuinely awkward. The current ordering quietly misrepresents the city.

**Data.** GTFS static again, plus a walk-to-station model.

**Build.** Large -- this is a routing problem, and a bad routing answer is worse than an
honest straight-line one. Rank is low for that reason, not for lack of value. Do #5 first;
it uses the same data and is a flag rather than an engine.

### 12. Is it streaming instead

**What it is.** On the film sheet, whether the film is already on a service he has, in
Mexico.

**Why him.** Genuinely changes the decision, and it is the question he will ask about every
arthouse title he has not heard of.

**Data.** TMDB watch providers, region MX, free with a key, JustWatch attribution
required. Needs a title-to-TMDB-id match, which is fuzzy for Spanish release titles -- the
`o` original-title field makes it much easier.

**Build.** Medium. Baked at build time, so no runtime key in the page.

### 13. The cheap day, not the price

**What it is.** Say which day each chain discounts, instead of trying to keep peso figures
current.

**Why him.** He asked for pricing, and the API publishes none -- confirmed, `/prices/`
does not exist. His V array carries hand-sampled prices tagged verified, likely and
unknown, and several already read "not sampled (promo week)". A peso figure decays in
weeks. "Wednesday is the cheap day" does not, and it is the fact he can actually act on
every week.

**Data.** Hand-kept, small, stable.

**Build.** Small.

### 14. Cinemex Loop, explained once

**What it is.** A one-screen reference on the loyalty program, plus the one derived number
that matters.

**Why him.** He asked for loyalty and points. The mechanics are real and checkable: four
tiers (One, Red, Gold, Platino) at 3%, 5%, 8% and 10% back, one point per peso, Gold at 12
visits a year, Platino at 24, points expire 12 months after they are earned. What the app
cannot do is show *his* balance -- there is no loyalty endpoint and it is logged-in only.
So this is a reference card, not a feature, and it should be built as one.

**Data.** Static, verified from Cinemex's own terms page.

**Build.** Small. Do not promise a points balance.

### 15. Make the map colours decode themselves

**What it is.** Since the legend is gone by his own instruction, have the map explain
itself another way -- colour keyed to whichever filter is active, or a one-line caption
naming what is currently shown.

**Why him.** He was right that the legend was clutter. The consequence is that four
meaningful colours now mean nothing to a viewer. A legend is a thing you read; a caption
that changes with the filter is a thing you cannot help absorbing.

**Data.** None new.

**Build.** Small.

### 16. Sister-site fallback

**What it is.** "Not at your local, but it is at its sister site" using `alt_cinemas`.

**Why him.** This is Cinemex's own linkage -- how Reforma 222 relates to Reforma Casa de
Arte -- present on 17 of 70 CDMX cinemas and unused. It is exactly the arthouse-overflow
case he cares about.

**Build.** Small.

### 17. Free tonight

**What it is.** Surface the free venues as a group. **13 of the 42** venues are free
outright and two more are sometimes free -- the Goethe-Institut at "$50 / free" and the
Centro Cultural Jose Marti at "$22 / free".

**Why him.** Thirteen free screening rooms inside his radius is a genuinely surprising fact
about where he is moving, and it is currently spread across thirteen separate write-ups. The
honest limit: none of them publish showtimes a page can read, so this links out to their
programme rather than listing times. Say that plainly instead of implying coverage.

**Build.** Small.

### 18. Is there a bar

**What it is.** One boolean per venue: real bar on site.

**Why him.** This is the salvageable grain of his snacks-and-drinks item. Whether a venue
has a bar is a stable property of the building, unlike a menu -- Cine Tonala has a cocktail
bar, Reforma 222 has a food hall, Centro Cultural de Espana has a rooftop bar. **4 of 42**
venues already say so in their prose. Promote it to a field and stop there.

**Build.** Small.

### 19. Search the director, and clean the director field while you are there

**What it is.** Add `dir` to `matchesQuery` -- and repair the values first.

**Why him.** "nolan" returns nothing today while La Odisea is playing at 25 cinemas with
264 showings. Adding `dir` to the search **would not fix it**, because Cinemex's own data
says `"Christopher Nola"`. Their director strings are truncated and dirty: another reads
`"Reedicion 2026: Maria Jose Cuevas. Direccion 1990: Benjamin "`, cut off mid-word.

So the two-line fix is a trap, and this is the useful shape of the idea: fold `dir` into
the search *and* keep a small correction table for the names that are visibly broken, the
way the venue audit already tags claims verified, likely and unknown. Ranked last because
it is small, but it is the kind of small thing that would otherwise ship looking fixed and
still return nothing for the most famous director playing in the city.

### 20. Watchlist import -- and the argument against it

**What it is.** Pull a Letterboxd watchlist and mark those films in the listings.

**Why him.** In principle: the "I have been meaning to see that" list meeting the "it is
playing 300 m away" list is the best idea in cinema software, and it is precisely what
**Letterboxd's own Now Showing does not do for Mexico** -- their showtimes run through the
aggregator Assemble across roughly 9,000 screens in the US, Canada, UK, Ireland, New
Zealand and Australia. Mexico is not in it. That gap is real and it is his.

**Why it is ranked last anyway.** Letterboxd's official RSS is `/<user>/rss/` and it
carries the last 50 films *watched* plus three lists -- not the watchlist. Watchlist feeds
are all third-party scrapers. So this needs an account he may not have, a scraper that will
break, and it only pays off for the small overlap between an arthouse watchlist and a
Cinemex multiplex. Build #6 first: "the screenings that happen once" serves the same
appetite using data he already has and nothing that can break.

### Where these came from

Naming the source, because a borrowed idea is easier to judge when you can see what it
looked like working somewhere else.

- **Alamo Drafthouse** -- their app's whole pitch is knowing the room before you buy: you
  flip through showtimes and see the seats for each. Ideas #3 and #5 are that instinct
  without a seat map, which Cinemex does not expose.
- **MUBI GO** -- one hand-picked film a week with its showtimes, redeemed same-day, rather
  than a grid of everything. Ideas #6 and #7 are that shape: a short list of things worth
  going to, ordered by when they happen.
- **Letterboxd Now Showing** -- built with the aggregator Assemble across roughly 9,000
  screens in the US, Canada, UK, Ireland, New Zealand and Australia. **Mexico is not in
  it.** That absence is the whole opportunity, and it is also the argument for ranking
  their watchlist idea (#20) last: what Letterboxd is good at is the film graph, and what
  it cannot do here is the showtimes, which he has already built.
- **Google's showtimes panel** -- the one thing it does better than anyone is answering
  "what is on near me right now" in one glance with no navigation. That is what the
  "starting soon" chip already is, and #1 is the version that also tells him to stand up.
- **Cinemex's own app** -- the loyalty tiers (#14) and the cheap-day promotions (#13) are
  theirs, and the honest note is that neither is reachable without a login, so both belong
  in this app as reference rather than as features.
- **Cineteca Nacional's own site** -- programming by cycle and by season, not by week. The
  79th Muestra Internacional ran across three sedes over four weeks. Any view of Cineteca
  built on a seven-day rail misrepresents it, which is most of why #6 exists.

## 5. The top three, far enough to start tomorrow

These three, in this order: **leave-by times, stacking filters, and which room**. Between
them they turn three numbers the app already holds into three decisions it currently makes
him work out himself, and none of them needs a new data source.

Idea #4 -- merging the duplicated films -- is not in the top three because it is a defect
rather than a feature, but it is a couple of hours in the Python and it should go in ahead
of all of them, because #6 and #7 are built on it.

### Leave-by times

Add one constant and one helper, then a second line on the chip.

```
const REEL = { cinemex: 17, cineteca: 3 };   // minutes of ads before the billed time
```

`renderShows()` already has the cinema in scope when it draws each chip, and the walk time
is already computed there for the header. So:

- `leaveBy(session, cinema) = session_minutes + REEL[chainOf(cinema)] - walkMinutes(cinema)`
- Draw it only when the chip is not `past`. A chip that has already started should keep
  saying what it says now.
- The existing `soon` class fires at 75 minutes; leave-by makes that threshold wrong.
  Re-point `soon` at "leave in the next 20 minutes", which is the thing that is actually
  urgent.
- Cineteca's reel allowance genuinely differs from Cinemex's and that difference is worth
  surfacing in the format glossary, not hidden in a constant.

Verification that would catch a wrong sign: a cinema 23 minutes away with a 20:30 showing
must produce a leave-by earlier than 20:30, and a cinema 4 minutes away must produce a
later one. Assert both, because an inverted subtraction looks plausible on one row.

### Stacking filters

`S.filter` is a string in five places. Make it a `Set`.

- `passes(fmtIdx, mins, dayIso, which)` currently `switch`es on one key. Split it into
  `passesOne(key, ...)` keeping today's cases verbatim, then
  `passes(...) = [...active].every(k => passesOne(k, ...))`.
- `filterCounts()` must count each chip against **the set plus that chip**, not the chip
  alone, or the numbers will contradict the list the moment two are active.
- The existing fallback `if (!counts[S.filter]) S.filter = "all"` becomes: drop any chip
  from the set that would take the count to zero. Keep that behaviour -- a chip that finds
  nothing being disabled is one of the better things in the app.
- `"all"` stops being a filter and becomes "clear the set".
- Persist the set to `localStorage` under `sala.filters`, next to `sala.theme`. Restore on
  boot, but drop `now` on restore -- "starting soon" is never a preference, only a mood.
- The count line's label is built from a lookup keyed by one filter. With a set it needs to
  compose, and "348 subtitled IMAX showings" reads better than any generic join will.

The control that proves it works: with Subtitled and IMAX both active the count must be
**126 across the payload and 9 for today**, both of which I measured, and both of which are
unreachable today.

### Which room

Add a structured sala table beside `V`, for the five venues whose audit already names salas.

```
const SALAS = {
  "Cinemex Parque Delta + Parque Delta Platino": {
    "Sala 3":  ["IMAX with Laser", "4K laser, 12-channel, 1.90:1"],
    "Sala 10": ["CinemeXtremo", "Dolby Atmos, also the Infinity Vision room"],
    "Sala 2":  ["Premium", ""],
  },
  // Antara, Reforma 222, Universidad, Galerias
};
```

- Session slot 6 already holds the room string (`"Sala 10"`), so the lookup is
  `SALAS[venueName]?.[s[6]]`.
- The join key is the problem, not the lookup: `SHOWS.cin[].n` is `"Parque Delta"` and
  `V[].name` is `"Cinemex Parque Delta + Parque Delta Platino"`. There is already merge
  logic pairing 19 cinemas across the two sources -- reuse that mapping rather than
  matching on strings a second time, or the two will drift apart.
- On the list, mark only the rooms that are better than the site's default. Annotating
  every chip would double the row height, which is the same problem the badge `cap`
  already exists to solve.
- In the sheet, where there is room, name the room properly.
- Guard it: assert that every room named in `SALAS` appears in at least one real session
  for that cinema. A table naming Sala 14 at a nine-screen site will otherwise sit there
  looking authoritative forever.

## 6. What I would drop from his own list

**Snack lists and drink lists. Drop them.** `candybar` is `false` on all 70 CDMX cinemas,
every candybar and product endpoint returns "No route found", and `cinemex.com/dulceria` is
a 404. There is no machine-readable menu anywhere. Building this means hand-typing menus
for 35 cinemas that reprice quarterly, and what he gets for it is a page confirming that
Cinemex sells popcorn. Keep only idea #18: one boolean for whether the venue has a real bar,
which is a stable fact about the building. Alcoholic drinks fold into the same boolean --
Cine Tonala's cocktail bar and the Centro Cultural de Espana's roof are worth knowing about;
a beer price is not.

**Average theater temperature. Drop it, and this is the weakest item on the list.** No
source exists, it varies by room and by hour, and the only way to get it is him carrying a
thermometer to 35 cinemas and then re-measuring in April. If the real complaint is that
Mexican multiplexes over-air-condition, the useful version is one sentence in the format
glossary saying so, once, for the whole city.

**Dress code. Drop it.** Mexican multiplexes do not have one, and Platino and VIP do not
enforce theirs. A field that answers "no" 42 times is not information. One clause in the
Platino glossary entry covers everything true here.

**Online reviews. Not as an aggregate rating.** Cinemex's own `score` field is 0 on all 51
films, so their rating is dead. Google's rating for a multiplex is a rating of the mall's
bathrooms and the queue, and it will not tell him whether to go. The Places API is metered,
which his own forever-free rule rules out -- though `tools/find-places.py` already gets
place ids and ratings off the endpoint Maps itself calls, so the free path exists and is
being worked on separately. My opinion on the substance: `availability` (high, medium, low)
is already in the page on all 11,252 showings and is a far better signal of whether a
showing is worth going to than a 3.9-star average. Spend the effort surfacing that.

**Loyalty and points. Keep, but as a reference card.** See #14. There is no API and no way
to show his balance; promising one would be a feature that cannot be built.

## 7. One design warning

The generic move here is obvious and should be named so it can be refused: a "For You"
carousel, star ratings on everything, a social feed, and an AI recommendation strip. Every
cinema app has arrived at that and it is why they are interchangeable. This app's whole
character is that it is quiet, that it says "unknown" when something is unknown, and that
it knows things about rooms that no chain publishes. Ideas #1, #3, #5 and #6 are all in
that voice -- they answer a question with a fact. Anything that replaces a fact with a
recommendation is working against the only advantage it has.

The second temptation is to fill the map. It has 60 markers and a walking radius on a dark
vector basemap and it is legible. Every additional overlay -- Metro lines, heat, prices --
costs that. #15 is a caption, deliberately, and not a layer.
